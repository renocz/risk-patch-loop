## 0.10.1 (2026-11-24)

### False-negative measure: the draw no longer refuses a `risk.json` that holds the same finding twice
- The first real draw (the plan of 24 November 2026, tag 0.10.0) stopped with "duplicate findings in the inputs": on the author's host `risk.json` holds the same (image, CVE, package) on several lines (one per Trivy target or per installed copy), and the draw refused the whole file. A measure that cannot run on a real host was a defect found by using it, not by tests, which only had unique rows.
- Duplicates now collapse to one row before the draw, the one the score ranks highest (a tie broken by the content of the row, not by the order of the file); the population of the measure is the set of distinct findings. The manifest records `duplicates_collapsed` per host and `draw` prints it. The guard on identical ids in `draw()` stays. The score is untouched: `rpl/risk.py` and `rpl/inventory.py` are byte for byte those of 0.10.0, so the fingerprint of the score is the same.
- 7 new tests (`DuplicateRowsTest`), 6 failing or erroring before (the seventh, the guard in `draw()`, pins what already held); of 5 removals of the rules, 5 fail a test. Suite 683, Python 3.11 here; CI covers 3.9 and 3.12. The README test count (EN and FR) is 683.

### Inventory: `gated_hosts_file`, hosts behind an authentication gate outside the proxy labels
- The score's `internet-auth` level (factor 0.85 against 1.0) came only from a forward-auth middleware in the Traefik labels. A host protected by a gate outside the proxy (the owner's tunnel has an access gateway in front of some hosts) shows nothing in the labels, so every host of the tunnel list was read as `internet-no-auth`. On the owner's host, with the real tunnel list and no gate list, the findings with a fix were 15 ACT, 480 PLAN, 2,742 WATCH, against 18 ACT and 222 PLAN on 19 November, when a private gate list existed that the public code did not know. The score is an input of the false-negative measure and is frozen before the draw, so this had to be in before.
- New optional key `gated_hosts_file`, a JSON list of host names, resolved next to the configuration like `tunnel_hosts_file`. A container whose every published host is listed there (or has a forward-auth label) is `internet-auth`; one router with an unlisted host, or without any host, keeps it `internet-no-auth`. The inventory gets a `gated` field (true when the gate list, not the labels, made it `internet-auth`), `auth` still means "the labels say so", and `rpl inventory` says how many gated hosts it believes. The list is believed, not tested; it only counts for hosts also in the tunnel list; it never makes a LAN level "-auth" (a request from the LAN straight to the proxy does not pass a gate that sits in the tunnel). A gated list that is not a JSON list of non-empty strings is an error, not an empty list; a configured file that does not exist is said in a warning and treated as no gate. Without the key nothing changes.
- 13 new tests (inventory, the reader, the configuration path, `inventory.main` with a fake Docker and files on disk), 12 failing or erroring before; of 11 removals of the rules, 11 fail a test (a first run left one survivor, a router without a host name; fixed). Suite 630, Python 3.11, 3.12, 3.13. README (EN and FR) and `examples/rpl.json` document the key.
- Not verified: the owner's real gate list; that a listed host is really gated.

### Group apply: `ignore_sockets`, for a socket the application creates again
- On the owner's real VPN group the plan reached the backup check and was refused: `qBittorrent/ipc-socket`, a Unix socket qBittorrent creates in its configuration directory, is a special file and cannot be copied. A socket has nothing to restore (the application creates it again), but refusing all of them silently would loosen a safety rule, so the owner names them: `services.<svc>.ignore_sockets`, a list of paths relative to the mounted directory. A named path that is a socket is left out of the size, the copy, the read-back and the manifest; a named path that exists and is not a socket, or any other special file (a pipe, a device), is still refused, and the refusal of an unnamed socket now says how to declare it. The plan lists what is left out and the fingerprint covers it (only when declared: the fingerprint of a group without the option does not change). A rollback restores the directory without the socket. Bad declarations (absolute path, `..`, empty, not a list, not strings) are refused in words.
- 16 new tests (`TreeSockets` 9, `SocketsInConfiguration` 7 with sub-cases, on the model of Docker with real files and real Unix sockets), 13 of them failing or erroring before (the others pin what held: an undeclared socket and a copy without declaration are refused, the fingerprint without the option is unchanged); of 14 removals of the rules, 12 fail a test and 2 survive (equivalent: the check after the loop refuses the same case). A first run showed a test that passed for a wrong reason (a string declared as `ignore_sockets` was iterated by character and refused as "not a socket"); it now requires the validation message. Suite 602, Python 3.11, 3.12, 3.13.
- Not verified: a real qBittorrent group on the owner's host; what the application does when its socket is absent or stale after a rollback; a socket named in a mount that is a single file.
### False-negative measure: a draw that works on a host with few ACT rows, and a decision rule instead of a pass mark
- On the owner's host (18 ACT, 222 PLAN, 1,902 WATCH findings with a fix, from a `risk.json` of 19 November 2026) the draw, which required ACT and PLAN + WATCH rows to be equally numerous, could not give 100 rows (it refused; `--allow-short` gave 36). It now takes the ACT rows in full (up to half the sample) and fills up to the size with PLAN and WATCH rows, as evenly as they allow; an odd size is met exactly. The result's weighting (previous entry) is what makes that sample usable.
- Roadmap criterion 2 no longer has a pass mark: "at most 10% missed" cannot be shown by sampling on such a host. `rpl sample result` applies a decision rule on the 95% interval for the host: the score must change and the measurement be repeated when the LOWER end is above 10%; otherwise it prints that the rule requires no change and that this does not show the rate is under 10%. README (EN and FR) and `docs/results.md` say so.
- 9 new tests (`FeasibleDrawTest` 8, including the 18 / 222 / 1,902 case, a small PLAN and a small WATCH stratum, odd sizes, determinism and the population sizes in the manifest; one for the decision rule), 8 of them failing or erroring before; one existing test changed on purpose (the trial draw of 6 + 6 + 6 findings now gives 18 rows, not 12). Of 9 removals of the rules, 9 fail a test (a first run left three survivors, the case of a small WATCH stratum, the printed upper end and the message without sizes; fixed). Suite 610, Python 3.11, 3.12, 3.13.
- Not decided, written down: a tighter interval by screening all the rows below ACT with a panel of models and auditing a part (it would send the rows of the host to outside providers).

### False-negative measure: the rate is estimated for the host, weighted by stratum
- `rpl sample draw` takes as many ACT rows as PLAN + WATCH rows, whatever their number in the host, but `rpl sample result` counted the 'act' answers without weights: it described the sample, and understated the rate whenever the rows below ACT are more numerous than the ACT rows (invented example: 200 ACT and 2,000 below ACT, 60% 'act' among the ACT sample and 6% below: the old code printed 9%, "target met", where the rate for the host is 50%). `result` now prints both: the rate in the sample (labelled as such) and `estimated for the host`, weighted by the size of each stratum (the manifest's `available_with_fix`), with a conservative deterministic interval (Wilson per stratum at the level that gives 95% for the three together, the ratio's ends taken at the corners). The 10% target is judged on the host estimate only. The JSON output has a `weighted` key. A sample drawn without the strata sizes is still read, with "cannot be estimated for the host".
- 15 new tests (`WeightedRateTest`, `ResultCommandWeighted`): the 9% against 50% case, ends worked out by hand, coverage of at least 95% by simulation with a fixed seed, zero misses is not a zero-width interval, an unlabelled stratum is reported; of 10 removals of its rules, 10 fail a test (a first run left three survivors: the corner ends, the correction constant and the `unsure` case; fixed). Suite 601, Python 3.11, 3.12, 3.13.
- Not changed: the draw, the sheets, the criteria. Found while checking, written in `docs/results.md`: the interval is wide (mean width 0.4 to 0.8 with 100 labelled rows in the cases simulated), so a sample of about 100 can show a high miss rate but cannot demonstrate a low one when the host has thousands of rows below ACT; the roadmap's 10% target needs a decision.
### notifs.json: a file this tool did not write is kept aside, never overwritten
- `notify.deliver` read `notifs.json` as an object, and treated anything else (a JSON list, text, a file it could not read) as empty, then wrote its own state over it: another tool's state in the same directory (a service of the owner, another version) was destroyed. Found while checking the migration of the owner's production, which keeps its own `notifs.json` and `apply.lock` in its state directory. Such a file is now moved to `notifs.json.unreadable-<stamp of its content>` (two different files are never mixed), a notice goes to stderr, and a fresh state is started: the alert is not held up. An object of another shape keeps its keys and gets this tool's next to them. A file this account cannot read is kept aside too.
- 8 new tests (`ForeignStateFile`), 5 of them failing or erroring before (the others pin what already held: an object keeps its keys, a readable state is never moved, a missing file is fine); of 6 removals of its rules, 5 fail a test and 1 survives (a renamed target that still starts with the same prefix). ### Notifications: a channel that confirmed an event is not sent it again

### Notifications: Retry-After, a timeout per channel, a time budget per run
- `rpl/notify.py`: `post` returns a `Status` (an int that may carry the seconds of a `Retry-After`); a failed event waits at least that long when it is longer than the calendar, never past one hour, the longest of the failing channels counting (a date or garbage is ignored). A plain integer returned by a poster keeps working.
- A channel may set `timeout_s` (seconds for one send, 15 by default, 60 at most; a bool, zero, a negative or a non-number is ignored). A run stops starting new sends after `run_budget_s` (45 s by default): the events left wait for the next run, and a held event is not a try. Before, a hanging channel held a run 15 s per channel and per event, which could outlast a one-minute timer.
- Critical events are never held by the budget: an event may carry `"critical": True` and `deliver` sends those first, whatever their place, and never holds one for time. Marked critical: everything `rpl watch` says (an apply that never finished, a failed rollback, an unreadable journal), a missing or failed nightly run, an unreadable state file, a patch that ended `rollback FAILED` or `aborted`. Not critical: a new application, an exclusion, a patch that worked, the group apply's "updated" and "rolled back" results. Found by a second opinion (a model council, 4 of 4 members "correct first", the starvation named a blocker by 2): five slow "updated" messages could have used the 45 s before a `CHECK BY HAND` placed after them.
- 4 cross tests (`Interactions`) check that the per-channel memory, `Retry-After`, the run budget and critical events hold together (a Retry-After on one channel holds the event and only that channel is retried; an event cut by the budget has no state and goes to every channel next time), written after the merge with the per-channel change, which touches the same function.
- 28 new tests (`RetryAfter` 9, `Timeouts` 4, `RunBudget` 9, `Critical` 2, `Priority` 4), 22 of them failing or erroring before (the others check that a plain status, no setting, fast sends, no flag and a new application still work); of 12 removals of its rules 12 fail a test (a first run had two survivors, a test where the longest hint came last and one for a record too old; fixed). The real `post` was tried against a local 127.0.0.1 server answering 429 and 503 with several `Retry-After` values; never against a real service.

### Notifications: notifs.json is written under a lock
- `rpl/notify.py`: `deliver` read `notifs.json` once and wrote the whole file at the end, so a run that overlapped another (`rpl watch` every minute, `rpl notify`, the group apply) erased what the other had recorded: a `delivered` mark (the event is sent again) or a `queued` one. It now reads the file again for each event and writes that event's state alone, after reading the file again, under an exclusive `flock` on `notifs.json.lock` (owner-only). The sends stay outside the lock. If the lock cannot be taken within `LOCK_WAIT_S` (5 s), or there is no `flock`, the write goes on without it: a lock must never stop an alert, and a duplicate message is better than a lost mark. A `notifs.json` entry of the wrong shape is replaced instead of raising `KeyError` (a duplicate is possible).
- Found by a second opinion (a model council, 3 of 4 members on the concurrency point), not by an incident. 7 new tests (`tests/test_notify.py::Concurrency`), 6 of them failing before (the lock-wait test is timing-based, lower bound only); suite 509 on Python 3.11, 3.12, 3.13. Removing each of 8 rules in turn: 6 removals fail a test, 2 survive (an `OSError` raised at the lock timeout is caught and ends the same way; the per-process temporary file name cannot be told apart from a shared one without two real processes).
- Not done: a test with two real processes; two runs can still both send the same event; the group apply's own messages are still given to `deliver` once.
### Notifications: a failed rollback is re-presented until it is acknowledged

Found by the supervised trial of 23 November 2026 and confirmed by reading the code; a second opinion (a model council, 4 of 4 members) asked that a `CHECK BY HAND` survive the failure of the first send.
- `rpl watch` now also reports every journal entry whose result starts with `rollback FAILED` while its backup directory exists (or names none): the alert is printed on every run, exit code 1, no grace and no time window. Its message is sent under the group apply's key (`watch.group_key`, now used by the group apply for its three messages), so a message that did arrive is not sent twice and one that did not is retried at each run, with the delay of `rpl/notify.py`. Acknowledgement needs no new command: `rpl group --purge` never deletes that backup, and deleting it by hand, once the services are repaired, ends the alert.
- 12 new tests in `tests/test_watch.py` (`FailedRollback` 11, `Key` 1), 11 of them failing or erroring before (the 12th checks that a successful rollback is not an incident); one test that said a failed rollback was not this check's business was removed on purpose (it asserted the old behaviour), so the suite grows by 11. ### Group apply: one notification per apply

### Group apply
- `rpl group --compose F --parent P` now applies a group (`rpl/groupapply.py`), only when a member has a proven security fix pending: plan from the compose file and from Docker (the two must name the same members), policy, rehearsal, controls, snapshot, journal entry, members stopped (`quiesce: stop`, default for a member that mounts a configuration directory), backup of the configuration directories under the compose file's directory (owner-only, modes, owners and symlinks kept, re-read), new images pinned by digest, parent recreated then every dependant, controls; on failure, per-member restore and recreation in order, verified (exit 2), or `CHECK BY HAND` (exit 4).
- Policies, now enforced: `auto` (nightly run, no human), `ask` (a human passes `--approve <fingerprint>`), `never`; `auto` and `ask` need `confirmed: true`; per-service `policy` and `quiesce` under `services`; the most restrictive policy wins. The group is declared under the parent's container name.
- `--plan` prints the plan and its fingerprint and proves that every configuration directory copies and reads back, without changing anything. `--resume` rolls back an interrupted apply; until then every group apply is refused. `--purge` deletes group backups older than `group_backup_retention_days` (7). New settings: `group_backup_retention_days`, `group_backup_max_mb`.
- `rpl fixcheck` records `candidate_digest`, the digest of the candidate it scanned (identical before and after the scan, otherwise null). The group apply refuses a fix whose digest is missing, cannot be read from the registry, or differs from the one the registry serves now.
